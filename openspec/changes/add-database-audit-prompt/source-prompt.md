# Universal Database Performance, Query Optimization, Relationships & Security Audit

## Primary Objective

Perform a comprehensive, project-wide audit of the current application's database architecture, SQL queries, relationships, loading performance, and database security.

Automatically identify the project's technology stack, database engine, ORM/query builder, and database architecture.

Find and fix performance bottlenecks, inefficient queries, missing or incorrect indexes, N+1 query problems, poorly designed joins and relationships, slow-loading pages, and SQL injection vulnerabilities.

**This is a complete audit, optimization, implementation, testing, and verification task — not just a code review.**

The final result must be a faster, more scalable, secure, and production-ready application without changing existing business logic or breaking functionality.

---

## Phase 1: Project & Database Discovery

Before modifying anything:

1. Analyze the entire codebase and identify the framework, ORM, query builder, database driver, and database engine/version.
2. Inspect database configuration, connection settings, migrations, models, repositories, services, controllers, API endpoints, and database-related background jobs.
3. Identify all database connections, including primary, replica, and external databases where applicable.
4. Analyze the database schema, including tables, columns, primary keys, foreign keys, indexes, constraints, and relationships.
5. Identify high-traffic modules and database-heavy workflows.
6. Review the existing caching, pagination, eager loading, and query optimization strategies.
7. Check whether database monitoring, slow query logging, and performance profiling are already configured.

Understand the existing architecture and project conventions before introducing changes.

## Phase 2: Application Loading & Performance Testing

Perform a complete application performance audit.

Test all major pages, API endpoints, and workflows that involve database operations.

Use available browser automation, HTTP benchmarking, application profiling, database monitoring, and testing tools.

Measure:

- Page loading time
- Time to First Byte (TTFB)
- Backend response time
- Database execution time
- Number of SQL queries per request
- Total database time per request
- Slowest queries
- Memory consumption
- CPU usage where measurable
- Database connection usage
- Query throughput
- p50, p95, and p99 response latency
- Application performance under concurrent requests

Identify pages and endpoints that become slow as database records increase.

Pay special attention to listing pages, search, filtering, sorting, product details, dashboards, reports, checkout, and other database-intensive workflows where applicable.

Create a measurable baseline before making changes.

## Phase 3: Identify the Slowest SQL Queries

Inspect all SQL queries generated by the application.

Use database-specific tools such as:

- EXPLAIN / EXPLAIN ANALYZE
- MySQL Performance Schema
- PostgreSQL pg_stat_statements
- SQL Server Query Store / execution plans
- ORM query logging and profiling
- Existing APM or slow-query monitoring

Select the tools appropriate for the detected database engine.

Identify:

1. Highest execution-time queries
2. Most frequently executed queries
3. Queries with the greatest total cumulative database cost
4. Queries performing full table scans unnecessarily
5. Queries scanning significantly more rows than they return
6. Queries with expensive sorting, grouping, or aggregation
7. Queries creating large temporary tables
8. Queries using inefficient joins
9. Queries with unnecessary subqueries
10. Queries with incorrect pagination patterns
11. Queries fetching unnecessary columns or records
12. Queries with poor filtering or search performance
13. Queries causing lock waits, blocking, or deadlocks
14. Queries responsible for excessive database connections or resource consumption

Rank problems by their actual performance impact.

**Important:** Query execution frequency matters as much as individual execution time. A moderately slow query executed thousands of times may be more expensive than a single slow query.

Use production-derived statistics when safely available, but avoid running expensive diagnostic queries against a busy production database.

## Phase 4: Database Indexing Audit & Optimization

Inspect every important table and query pattern.

Check:

- Missing indexes
- Incorrect indexes
- Duplicate indexes
- Redundant indexes
- Unused indexes
- Indexes on frequently filtered columns
- Foreign key indexing
- Indexes supporting JOIN conditions
- Indexes supporting ORDER BY
- Indexes supporting GROUP BY
- Composite indexes
- Composite index column ordering
- Covering indexes where beneficial
- Unique indexes and constraints
- Search-related indexes
- Index selectivity and cardinality
- Index maintenance overhead

Review query execution plans before deciding which indexes to add.

Do not add indexes blindly to every column.

Choose indexes based on actual WHERE, JOIN, ORDER BY, GROUP BY, and workload patterns.

Consider write-performance overhead, table size, index size, and the existing database engine's capabilities.

Apply safe, reversible migrations when index changes are justified.

After implementation, compare query execution plans and execution times.

## Phase 5: JOIN & Relationship Optimization

Analyze all database relationships and SQL joins.

Review:

- One-to-one relationships
- One-to-many relationships
- Many-to-many relationships
- Polymorphic relationships where supported
- Pivot and junction tables
- Nested relationships
- Foreign keys
- Referential integrity
- Cascading rules
- Relationship loading behavior

Identify and correct:

- Incorrect JOIN conditions
- Unnecessary JOIN operations
- Missing JOIN indexes
- Cartesian products
- Duplicate rows caused by incorrect joins
- Expensive nested relationships
- Incorrect INNER JOIN / LEFT JOIN usage
- Inefficient relationship filtering
- Missing foreign key constraints
- Orphaned relationship records
- Unnecessary repeated relationship queries
- Incorrect ORM relationship definitions

Ensure that changes preserve existing business logic, nullable relationships, and intended data behavior.

Do not automatically delete orphaned data or introduce destructive cascading relationships.

Report data integrity issues and handle them through safe, explicit remediation strategies.

## Phase 6: N+1 Query Detection & Elimination

Perform a dedicated N+1 query audit across the entire project.

Inspect:

- Controllers and route handlers
- ORM models
- Service layers
- API resources and serializers
- Templates and views
- Nested components
- Loops accessing relationships
- Dashboard widgets
- Background jobs
- GraphQL resolvers where applicable
- Export and reporting workflows

Identify situations where one query loads a collection and additional queries are executed for each item.

Fix N+1 issues using appropriate techniques:

- Eager loading
- Explicit preloading
- Batched queries
- Data loaders
- Relationship count aggregation
- Efficient joins
- Bulk fetching
- Selective field loading

Avoid excessive eager loading that unnecessarily increases memory consumption.

Ensure query counts remain bounded as the number of records increases.

Create regression tests that detect reintroduced N+1 problems.

## Phase 7: SQL Query Rewriting & ORM Optimization

Review inefficient queries throughout the codebase.

Optimize where appropriate:

- SELECT * usage
- Unnecessary column selection
- Repeated database calls
- Inefficient loops executing queries
- Expensive correlated subqueries
- Redundant joins
- Inefficient aggregation
- Excessive COUNT queries
- Unnecessary DISTINCT usage
- Inefficient wildcard searches
- Non-sargable filtering conditions
- Repeated relationship loading
- Inefficient pagination
- Large OFFSET pagination where keyset pagination is suitable
- Excessive database round trips
- Unnecessary model hydration
- Oversized result sets

Prefer framework-native query builders and ORM capabilities when they produce efficient, maintainable queries.

Use raw SQL only when justified and safely parameterized.

Optimize for database workload, query execution plan, maintainability, and correctness rather than shorter code.

## Phase 8: SQL Injection & Database Security Audit

Perform a thorough SQL injection vulnerability assessment.

Inspect every entry point where external input can influence database queries.

Review:

- Search inputs
- Filtering and sorting parameters
- URL/query-string parameters
- Form submissions
- API request bodies
- Authentication queries
- Dynamic SQL construction
- Raw SQL statements
- Stored procedures
- Database queries in background jobs
- Administrative search and reporting interfaces
- Dynamic table names and column identifiers

Identify vulnerabilities involving:

- SQL string concatenation
- Unsafe interpolation
- Unparameterized raw queries
- Improper escaping
- Unsafe dynamic ORDER BY values
- Unsafe dynamic table/column names
- Second-order SQL injection
- Trusting previously stored user-controlled values
- Unsafe stored procedure construction

Fix vulnerabilities using:

1. Parameterized queries and prepared statements.
2. Framework-native safe query builders.
3. Strong input validation where appropriate.
4. Allowlisting for dynamic identifiers and sort directions.
5. Proper authorization and permission checks.
6. Least-privilege database accounts.
7. Secure handling of database credentials.

Do not rely on string escaping as the primary SQL injection defense.

Perform authorized security regression testing using safe, non-destructive test cases in a controlled environment.

Never expose credentials or sensitive customer data in logs or reports.

## Phase 9: Database Schema & Data Integrity Review

Inspect the database structure for scalability and correctness.

Check:

- Primary key consistency
- Foreign key correctness
- Missing relationship constraints
- Incorrect data types
- Nullability inconsistencies
- Unnecessary columns
- Duplicate data
- Missing uniqueness constraints
- Incorrect default values
- Relationship integrity
- Data type compatibility in joins
- Oversized columns
- Unnecessarily expensive schema patterns
- Schema drift between migrations and the actual database

Identify schema issues that negatively affect query performance or data integrity.

Only apply schema changes when justified, backward-compatible, and verified.

For destructive or high-risk schema changes, prepare a migration plan and obtain explicit approval before execution.

## Phase 10: Caching & Database Load Reduction

Analyze the existing caching strategy.

Identify expensive database operations that could safely benefit from caching.

Consider:

- Frequently accessed read-only data
- Repeated aggregate queries
- Configuration and lookup data
- Expensive dashboard metrics
- Common catalog and category queries
- Search result caching where appropriate
- ORM query/result caching
- Application-level caching

Use the existing caching architecture when possible.

Ensure:

- Appropriate cache expiration
- Correct cache invalidation
- Tenant/user-specific cache isolation
- No leakage of personalized or sensitive data
- No stale checkout, inventory, payment, or permission data
- Safe behavior when caching is unavailable

Do not use caching to hide fundamentally inefficient SQL queries.

Optimize the query first where reasonable.

## Phase 11: Database Connections, Transactions & Concurrency

Audit database connection handling and transaction management.

Inspect:

- Connection pooling
- Connection leaks
- Idle connections
- Connection timeouts
- Transaction duration
- Nested transactions
- Lock contention
- Deadlocks
- Isolation levels
- Retry behavior
- Long-running transactions
- Batch inserts and updates
- Background job concurrency
- Read/write splitting where applicable

Identify issues that can cause slow responses, connection exhaustion, inconsistent data, or reduced throughput.

Optimize safely while preserving transactional correctness.

Pay special attention to inventory, orders, payments, and other operations where concurrent requests can create data inconsistencies.

## Phase 12: Large Dataset & Load Testing

Test the application's database performance under realistic data volumes.

Use representative datasets and realistic query patterns.

Perform controlled tests for:

- Small datasets
- Medium datasets
- Large datasets
- Concurrent users
- Repeated API requests
- Search and filtering
- Sorting and pagination
- Complex relationships
- Bulk operations
- Dashboard aggregation
- Background processing

Measure how query count, response time, and database resource usage change with dataset size.

Do not perform disruptive stress tests against production.

Use a staging or isolated test environment for resource-intensive testing.

Identify queries that scale poorly and optimize them.

## Phase 13: Implement Fixes

After identifying and prioritizing issues, implement the necessary improvements.

Follow these priorities:

**Priority 1 — Security & Correctness**
- SQL injection vulnerabilities
- Broken relationships
- Incorrect query behavior
- Critical integrity issues

**Priority 2 — Critical Performance**
- Severely slow queries
- Missing high-impact indexes
- Major N+1 problems
- Database connection bottlenecks
- Expensive high-frequency queries

**Priority 3 — General Optimization**
- Inefficient joins
- Repeated queries
- ORM improvements
- Pagination improvements
- Caching opportunities
- Schema improvements

**Priority 4 — Long-Term Scalability**
- Large dataset performance
- Monitoring
- Regression tests
- Database maintainability

Fix root causes rather than applying temporary workarounds.

Avoid unnecessary architectural rewrites.

## Phase 14: Automated Testing & Verification

After implementing changes, execute the available automated test suite and add relevant regression tests.

Verify:

1. All optimized queries return the correct results.
2. Existing business logic remains unchanged.
3. Relationships load correctly.
4. No new N+1 issues have been introduced.
5. Index changes improve relevant execution plans.
6. SQL injection regression tests pass.
7. Pagination, sorting, filtering, and searching work correctly.
8. Database migrations are safe and reversible where possible.
9. Concurrent operations preserve data integrity.
10. Previously working pages and API endpoints continue to function.

Compare performance against the original baseline using equivalent datasets, request patterns, and test conditions.

Record:

- Before/after query execution time
- Before/after SQL query count
- Before/after database time per request
- Before/after API response latency
- Before/after p95 and p99 latency
- Index utilization
- Overall database workload changes

Do not claim performance improvements without actual measurements.

## Phase 15: Production Safety Rules

This task may involve production-sensitive databases.

Follow these rules strictly:

- Determine the environment before making database changes.
- Prefer read-only inspection first.
- Never reset, truncate, or drop production tables.
- Never delete customer, order, payment, or other business records.
- Never run destructive migrations automatically.
- Never expose database passwords, API secrets, or sensitive records.
- Do not enable expensive unrestricted SQL logging in production.
- Do not execute resource-intensive EXPLAIN ANALYZE or load tests against a busy production database.
- Use staging or sanitized representative data for risky testing.
- Review backup availability and rollback strategy before applying schema changes.
- Use database-engine-appropriate migration techniques to minimize blocking.
- Preserve backward compatibility when the application requires it.
- Ask for explicit approval before destructive or operationally high-risk production changes.

Safe code-level optimizations and verified low-risk improvements should be implemented rather than merely recommended.

## Definition of Done

The task is complete when:

- All accessible major database queries have been audited.
- High-impact slow queries have been optimized.
- Necessary indexes have been reviewed and safely implemented.
- Joins and ORM relationships have been verified.
- Confirmed N+1 problems have been fixed.
- Identified SQL injection vulnerabilities have been remediated.
- Application loading and database response times have been tested.
- Database correctness and data integrity are preserved.
- Relevant automated and regression tests pass.
- Performance improvements are supported by before-and-after measurements.
- Outstanding risks and untested areas are transparently documented.

## Final Execution Instruction

Work autonomously within the current project.

Start with architecture discovery and baseline measurements.

Then identify bottlenecks, analyze root causes, implement safe optimizations, and verify each improvement.

Use the appropriate framework-specific, database-specific, and available profiling tools.

Do not stop after preparing an audit or proposing solutions.

**Expected result: A thoroughly tested, secure, optimized, scalable, and production-ready database layer with efficient queries, correct indexes, reliable relationships, no confirmed N+1 regressions, and no known SQL injection vulnerabilities in the audited scope.**
